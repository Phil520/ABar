# 开发笔记：菜单栏状态项不渲染的排查记录

2026-10-21。做「指数条」时踩的最大的坑，记下来免得下次重走。

## 现象

代码跑起来了，进程在，`statusItem.button.window` 也报了
`frame=(565.0, 923.0, 126.0, 33.0) screen=(0,0,1470,956) visible=true`，
菜单栏上就是没有东西。截图里那一整段是空的。

## 唯一的关键对照

同一个项目目录下：

- **CodexO（project028）重启后图标照常显示**
- 本工具、以及从零写的 30 行最小 app（同样 bundle、LSUIElement、ad-hoc 签名）**都不显示**

`CGWindowListCopyWindowInfo` 按 pid 过滤，两者都是 `0` 个窗口；
但 CodexO 自己的诊断日志在「拷贝到 /tmp」那一轮里也写着
`窗口可见: true / 系统窗口列表中的本进程窗口数: 0`——说明这个指标本身不可靠，
别拿它当判据。

结论落在系统侧：**新建的状态项被布点到一个不渲染的区域**（本机菜单栏上那一段
500–1000pt 的空档，就是这些不可见项占着的）。CodexO 因为槽位早已注册所以不受影响。
这一类的正解只有一个：重启（或注销重登）。

## 下次的省事路线

1. 先 `pgrep` 确认进程在 → 在就说明代码没问题，别改代码。
2. 退出所有菜单栏管理工具，重启 App 试一次。
3. 还不行 → 直接重启电脑，不要在代码里找原因。
4. 中途想验证「到底有没有上屏」，用最小复现程序比对自己的 App，别只看自己的日志。

## 顺带记下的两个坑

- `swiftc` 只允许名为 `main.swift` 的文件写顶层语句。测试文件不能直接编译，
  `build.sh` 里把它复制成独立临时目录的 `main.swift` 再编（每个测试各编各的）。
- `swiftc ... | grep error && exit 1` 的退出码是 `grep` 的，编译失败会被静默放过。
  一律先重定向到文件、再看 `$?`。

## 补充：位置值这条路也别走（10:50 再查）

`statusItem.autosaveName` 会在本 App 偏好里存一条
`NSStatusItem Preferred Position IndexBarItem`。本机实测各 App 的值：

| App | 位置值 | 实际落点 |
|---|---|---|
| ControlCenter BentoBox | 179 | 最右 |
| WiFi | 221 | 右 |
| Vorssaint | 291 | 右 |
| CodexO | 327 | 右（可见） |
| 指数条（初始） | 753 | x=565（不可见区） |

看着像「值越大越靠左」，于是我逐个改值试探：260 → x=1438（被时钟盖住）、
340 → x=1389、480 → x=0、560 → 又跳回 1438。**不单调、不可预测**，
说明系统侧这张排序表本身已经乱了（`uptime` 显示开机 69 天）。
结论不变：菜单栏内显示只能靠重启恢复，别在代码里找解。

## 补充：真崩过一次，问题在跨线程改 UI（10:53）

做悬浮窗降级时，App 一启动就崩，崩溃栈指到
`FloatingBarController.update` → `systemLayoutSizeFittingSize`：

```
This application is modifying the autolayout engine from a background thread
```

原因是 `URLSession` 的回调在线程池里，我直接在回调里改 `attributedTitle`
并触发了布局重算。修法：回调里 `DispatchQueue.main.async { ... }` 再动界面。

⚠️ 这个 bug 在菜单栏模式下不崩、只是不画——**「不崩」不代表「线程是对的」**。
以后凡是网络/文件回调里碰 UI，一律先回主线程。

## 2026-10-21 收尾：状态项不显示的真正原因

第一版折腾了很久都没在菜单栏出现，单文件重写（src2）后一次就上屏。
复盘下来是三层原因叠在一起，按发现顺序记：

### 一、判据错了

一路在用 `statusItem.button?.window?.frame` 判断有没有上屏。
在 macOS 26 上，状态项类是 `NSSceneStatusItem`，`button.window` 只是个**占位窗口**，
高度 22、y=-6 之类的值毫无意义；真正被控制中心托管的窗口高度是 33、y=923。

正确的判据只有一个：**窗口服务器的菜单栏层（layer 25）里有没有这块窗口**。
`tools/menubarcheck.swift` 就是照这个写的，build.sh 编译后自动跑。

```bash
x=  1170.0  w=81.0  h=33.0  L25  控制中心  "IndexBarItem"   ← 这才是上屏了
```

### 二、Hidden Bar 把新项挤出屏幕

`Hidden Bar` 会插一根宽 **5016 像素** 的占位条（`hiddenbar_separate`），
把「隐藏区」的项整体推到屏幕左边缘之外。新装的状态项默认落在隐藏区，
于是窗口 x 变成 -3952 这种值，屏幕上什么都没有。

位置值越小越靠右。实测这台机器上：折叠箭头 295、占位条 327，
任何大于 295 的值都会被挤出屏幕；设 150 落在 x=1170。

### 三、首屏窄字导致槽位不重排

建项时用「—」当首屏文字，系统按 32pt 默认宽度定好槽位；读数下来后窗口变宽到 81pt，
槽位却不往左让，右边 48pt 被切到屏幕外（x=1438 + 81 > 1470）。
首屏改用等宽占位串 `00000.00`，宽度一开始就是 81pt。

### 怎么定位到这层的

用对照法一步步缩小：同一个二进制换路径、换 bundle id、换包名、换 Info.plist，
分别跑；再把探针二进制塞进我们的 App 包里跑。最后这条最有价值——

> 探针二进制 + 我们的包 = 正常上屏
> 我们的二进制 + 任何包 = 不显示

说明包和配置干净，问题在可执行文件本身。于是放弃改第一版，改单文件重写。

### 教训

- 菜单栏工具的自检必须查窗口服务器，不能查进程、也不能查 `button.window`
- 遇到「怎么写都不显示」，先做对照（同一二进制换环境 / 换二进制同环境），别继续猜
- 别用 `kill -9` 收尾：控制中心会留下僵尸状态项，把后续所有对照污染掉
